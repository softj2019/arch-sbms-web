# SBMS 현행 시스템 분석 리포트 (1차)

## 문서 목적

이 문서는 `D:\home\sbms` 프로젝트의 현행 구조를 빠짐없이 파악하기 위한 1차 분석 리포트다.
이번 단계는 **현 상태 분석**에 집중한다.
다음 페이즈에서 이 분석을 바탕으로 유지보수, 협업, CI/CD, 자동배포, 차세대 전환을 위한 **고도화 방안**을 별도로 제시한다.

## 분석 범위

- 애플리케이션 구조와 실행 방식
- MVC 화면, REST API, WebSocket/STOMP 구조
- 현장 디바이스 연계 방식
- MCU/라즈베리파이 계열 장비로 추정되는 운영 페이로드 흐름
- HID/재실 감지, Wi-Fi/라우터, LED/전광판, 제어보드, 디스플레이 제어 흐름
- 기상/대기질 외부 API 연계
- 인증/권한/보안 구성
- 유지보수성, 협업성, 테스트, 운영성, CI/CD 자동배포 관점
- 향후 REST API 분리 + Swagger 기반 고도화 vs 차세대 재구축 판단을 위한 기초 자료

## 한눈에 보는 결론

이 시스템은 단순한 Spring Boot 웹앱이 아니라, **현장 설치형 스마트 버스정류장 운영 플랫폼**에 가깝다.
핵심 특성은 다음과 같다.

- 웹 관리 화면 + REST API + WebSocket(STOMP) + 일부 UDP 수신이 한 프로젝트에 결합되어 있다.
- 현장 디바이스 상태 수집과 제어가 브라우저와 디바이스 사이의 실시간 메시징에 강하게 의존한다.
- 기상/대기질 데이터가 정류장 운영 설정과 연결되어 있다.
- 프런트와 백엔드가 메시지 포맷과 토픽에 직접 결합되어 있어 기능 추가는 빠르지만 구조적 복잡도가 높다.
- 운영상 필요한 도메인 지식은 많지만, 코드/문서/테스트/배포 자동화는 그 복잡도를 따라가지 못하고 있다.
- Swagger 의존성은 있으나 API 제품 수준의 문서화/표준화는 아직 사실상 미구현 상태다.
- CI/CD, 테스트, 환경분리, 비밀정보 관리, 운영 가시성, 협업 표준화는 매우 취약하다.

즉, 이 프로젝트는 “동작하는 현장 시스템”으로서는 의미가 크지만, **유지보수와 협업, 자동배포에 유리한 제품형 구조로는 아직 리마스터가 필요한 상태**다.

## MCU/라즈베리파이 기반 실시간 연계 분석

사용자 설명대로 현장 MCU, 특히 라즈베리파이 계열 장치 기반 운영이라는 맥락이 코드와 잘 맞는다.
코드에 “Raspberry Pi”가 명시되지는 않지만, 다음 근거로 그렇게 추정할 수 있다.

- `MonitoringDTO` 필드명에 `rfc_cpu`, `cpu_temperature`, `rfc_memory_*`, `rfc_storage_*` 존재
- 현장 단말별 `terminal_id` 기반 실시간 상태 갱신
- 브라우저가 `/topic/dashboard`를 구독하고 단말 상태를 실시간 반영
- 디바이스 전원 상태가 별도 제어 항목으로 분리됨

이 판단은 **코드상 직접 명시가 아닌, 필드명과 동작 흐름을 근거로 한 추론**이다.

### 실시간 모니터링 수집 흐름

1. 현장 단말이 `/api/iot/overview`로 WebSocket 메시지 송신
2. `WebSocketController.handleData()`가 수신
3. 원문 메시지를 `/topic/dashboard`로 브로드캐스트
4. 동시에 `MonitoringService.processMessage()`가 JSON을 `MonitoringDTO`로 변환
5. `tb_monitoring` 테이블에 저장
6. 브라우저의 `dashboard.js`, `monitoring.js`, `screen.js`가 해당 토픽을 구독해 UI 갱신

### `MonitoringDTO` 페이로드 성격

- `terminal_id`
- `ipaddress`
- `rfc_cpu`
- `cpu_temperature`
- `rfc_memory_total`
- `rfc_memory_used`
- `rfc_memory_available`
- `rfc_storage_total`
- `rfc_storage_used`
- `rfc_storage_available`
- `ctl_board_power`
- `smartscreen_power`
- `led_panel_power`
- `led_light_power`
- `lcd_display_power`
- `lte_router_power`
- `vc_power`
- `fan`

이 구조는 단순 환경센서가 아니라 **OS/하드웨어/부속장치 상태를 함께 보내는 엣지 단말**에 가깝다.

### 구조적 특징

- 브라우저가 WebSocket을 직접 사용해 상태와 제어 응답을 받는다.
- 화면 로직이 토픽명과 페이로드 키를 직접 알고 있다.
- 메시지 버전 관리, 계약 검증, 스키마 관리가 없다.
- 인증된 사용자별 채널 분리보다는 브로드캐스트 중심이다.
- 운영 UI와 디바이스 제어 프로토콜이 강하게 결합되어 있다.

### 아키텍처적 의미

장점:

- 구현이 단순하고 반응성이 빠르다.
- 운영 대시보드 구현이 쉽다.

단점:

- 프런트/백엔드/디바이스가 토픽과 JSON 키에 강결합
- 계약 변경 시 회귀 범위가 넓음
- 메시지 감사 추적과 버전 호환이 어려움
- 멀티팀 협업과 API 제품화에 불리

## UDP 기반 Wi-Fi/라우터 연계 분석

이 시스템에는 WebSocket 외에 UDP 수신 경로도 존재한다.

### 흐름

1. `UdpListenerService`가 `55010` 포트에서 UDP 수신
2. 바이너리 패킷을 직접 파싱
3. 파싱 결과를 JSON으로 변환
4. `/topic/udp/data`로 브로드캐스트
5. 프런트 `wifi.js`가 구독해 Wi-Fi 상태를 실시간 갱신

### 추출 항목

- `device_type`
- `ctn`
- `ip_address`
- `mac_address`
- `imei`
- `firmware_version`
- `lte_version`
- `apn`
- `lan_ip`
- `wifi_mac`
- `wifi_enable`

### 특징

- 라우터/통신 모듈 상태를 운영화면에서 확인하려는 구조다.
- 프로토콜이 코드에 직접 하드코딩되어 있다.
- CRC, 길이 검증, 스키마 검증, 버전 호환 처리 등은 보이지 않는다.

### 운영 리스크

- 프로토콜 변경 시 서버 수정 필요
- 파싱 실패 처리 및 재시도 체계 미흡
- 고정 포트/직접 스레드 생성 방식이라 관측성과 제어성이 낮음

## HID/재실 감지 연계 분석

### 흐름

1. 디바이스가 `/api/iot/hid`로 WebSocket 메시지 송신
2. `WebSocketController.hid()`가 수신
3. `terminal_id`, `people_count`, `stat_people_count`, `file_name` 저장
4. `tb_hid_log` 계열 로그 조회 기능으로 운영자 화면 제공
5. `/topic/hid` 브로드캐스트를 통해 대시보드 반영

### 운영 의미

- 단순 로그 적재가 아니라 재실/이용량 지표로 활용하려는 의도가 있다.
- 이미지 파일명까지 함께 저장되는 점을 보면, 현장 캡처 이미지와 이벤트 로그가 연계될 가능성이 높다.

## LED/전광판/스크린/전원 제어 분석

### 제어 대상

- 스마트스크린 상하/정지
- 개별 디바이스 전원 제어
- LED 메시지 전송
- Shell command 전송

### 특징

- 제어 요청은 브라우저에서 STOMP로 직접 발행
- 서버는 해당 메시지를 사실상 재브로드캐스트
- 제어 명령의 최종 실행 주체는 현장 단말 또는 디바이스 측
- 일부 제어 로그는 REST API로 별도 적재

### 구조적 해석

현재 서버는 “명령 오케스트레이터”라기보다 **중계 허브**에 가깝다.
즉, 명령 상태 머신이나 ack/retry/timeout/command history 표준화보다, 우선 현장 즉시 반영에 맞춰 설계된 구조다.

## 기상/대기질 연계 분석

### 수집 대상

- 기상청 초단기 실황
- 공공데이터 대기질 측정

### 처리 방식

- `WeatherService.fetchAndSaveWeatherData()`
- 10분마다 호출
- 측정소/좌표/인증키가 코드에 하드코딩
- 수집 결과를 `tb_weather_air_quality`에 저장
- 최신값은 캐시로 조회
- `WeatherInsertDataService`에서 캐시 무효화

### 운영 연결성

기상/대기질 정보는 단순 조회용 위젯이 아니라 일부 설정과 연동된다.

- `/api/iot/config` 응답에 최신 온도 `t1h` 포함
- 설정값과 함께 현장 단말에 내려보내는 구조
- 즉, 환경 정보가 현장 동작 기준값과 간접적으로 결합되어 있다

이 점은 차세대 설계 시 매우 중요하다.
기상/대기질은 “정보 표시 기능”이 아니라 **운영 설정 입력값**으로 취급될 수 있다.

## REST API 현황

### 관찰된 API 범주

- 인증: 로그인, 로그아웃, 현재 사용자
- 대기질: 상태 목록, 상태 수정, 최신값
- 시설: 목록, 생성, 수정, 삭제, 중복 확인
- 명령: 명령 목록, 명령 등록
- 허용 IP: 목록, 생성, 수정, 삭제
- 제어 로그, 메시지, 대시보드
- HID 로그
- 사용자/권한/접속통계
- Wi-Fi 조회
- 이미지 업로드/조회

### API 성숙도 평가

현재 API는 “프런트 전용 내부 API” 성격이 강하다.

- URL 네이밍 일관성 부족
- `shallList`, `addShall` 같은 도메인/표준성 낮은 명명 존재
- 요청/응답 규격이 컨트롤러별로 다름
- 예외 응답 표준화 부족
- OpenAPI annotation 부재
- 버전 관리 부재
- 일부 엔드포인트는 사실상 화면 로직 보조용

## Swagger/OpenAPI 관점 분석

`build.gradle`에 `springdoc-openapi-ui` 의존성은 포함되어 있다.
하지만 코드상에서 다음은 보이지 않는다.

- OpenAPI 설정 클래스
- `@Operation`, `@Schema`, `@Tag`
- API 그룹 분리
- 응답 모델 표준화
- 문서화 대상/비대상 분리

즉, **Swagger는 사용 준비 상태가 아니라 의존성만 추가된 상태**로 보는 것이 맞다.

## MVC 화면 + REST + WebSocket 혼합 구조 분석

현재 구조는 다음 세 가지가 한 애플리케이션 안에서 강하게 섞여 있다.

- Thymeleaf 화면
- 내부용 REST API
- 디바이스 연계용 실시간 메시지 처리

이 구조는 초기 납기에는 유리하지만, 아래 비용이 커진다.

- 화면 변경이 API/메시지 계약 변경으로 이어짐
- 운영 화면과 디바이스 연계 도메인이 분리되지 않음
- 프런트 교체 난이도 상승
- 자동화 테스트 경계 설정 어려움
- 배포 영향 범위 확대

## 데이터 저장 구조 분석

코드상 식별되는 주요 테이블군:

- `tb_monitoring`
- `tb_terminal`
- `tb_terminal_devices`
- `tb_command`
- `tb_general_setting`
- `tb_weather_air_quality`
- `tb_weather_air_quality_status`
- `tb_wifi_info`
- `tb_user`
- `tb_role`
- 메뉴/권한 관련 `tb_rmmenu`, `tb_rmmenulink`
- 허용 IP, 제어 로그, HID 로그 관련 테이블

### 특징

- 운영성 테이블과 설정 테이블, 관리자 테이블이 혼재
- 일부 테이블은 최근값성 데이터, 일부는 이력성 데이터
- `tb_monitoring`는 3일마다 `TRUNCATE`
- 히스토리 보존 정책이 기능별로 제각각

### 의미

차세대화 시 저장소를 다음 관점으로 분리 검토할 필요가 있다.

- 실시간 최신 상태
- 이력성 이벤트
- 운영 설정
- 관리자/권한
- 외부 연계 캐시성 데이터

이번 단계에서는 분리 방안을 제안하지 않고, 현행 혼재 상태만 기록한다.

## 인증/권한/보안 분석

### 현재 인증 방식

- 로그인 후 JWT를 HttpOnly Cookie에 저장
- `JwtAuthenticationFilter`가 쿠키에서 JWT 추출
- 사용자 로딩은 JPA 기반

### 문제점

- `SecurityConfig`에서 `/api/**` 전체가 `permitAll()`
- WebSocket 연결도 사실상 전체 허용
- WebSocket inbound interceptor에서 인증 대신 `guest`를 넣음
- `IpMacSecurityFilter`는 코드 존재하지만 Security Filter Chain에는 연결되어 있지 않음
- CORS는 `*` 허용 + credential 허용 조합
- JWT blacklist 체크 코드가 주석 처리
- 쿠키 `secure=false`
- 비밀키와 DB 계정, 외부 API 키가 설정 파일/코드에 하드코딩

### 해석

“보안 기능이 없는 시스템”은 아니지만, **현행 보안은 운영 안정성보다 개발 편의와 현장 연결성을 우선한 상태**다.
협업, 자동배포, 외부 연동 확대를 생각하면 가장 먼저 재정비가 필요한 축 중 하나다.

## 환경설정 분석

### 프로파일

- 기본 활성 프로파일은 `prod`
- 같은 `application.yml` 안에 `dev` 프로파일 블록 존재
- `application-local.yml`, `application-prod.yml`도 별도 존재

### 문제점

- 설정 중복
- 환경별 책임 경계 불명확
- 일부 정보가 코드/설정에 하드코딩
- 운영 비밀정보가 저장소에 포함됨
- `application.yml`에 DB 자격증명, JWT secret, 외부 API key 존재

### 협업 리스크

- 신규 인원이 잘못된 운영 DB에 접속할 가능성
- 브랜치 실행만으로 운영성 외부 시스템 호출 가능성
- 환경 재현성과 배포 신뢰도 저하

## 프런트엔드 분석

### 특징

- 전통적인 jQuery 중심 구조
- 화면별 JS 파일이 데이터 조회, STOMP 구독, DOM 조작을 모두 담당
- 공통 데이터 일부가 `common.js`에 하드코딩
- 정류장 메타데이터가 프런트에 중복 존재

### 주요 문제

- 정류장명/장비 상태 샘플 데이터 하드코딩
- 화면별 상태 관리 중복
- 토픽/페이로드가 화면 코드에 직접 박혀 있음
- 타입 안정성 부재
- 빌드 체계가 프런트 현대화 수준에는 못 미침

## 유지보수성 분석

### 강점

- 기능이 도메인별 서비스/컨트롤러로 어느 정도 분리되어 있음
- 현재 운영 요구사항을 빠르게 반영하기 쉬운 구조
- 실시간 운영 화면 기능은 이미 구현 경험이 축적되어 있음

### 약점

- 서비스/컨트롤러 책임 경계가 고르지 않음
- 화면, API, 메시징, 인프라 코드가 혼재
- 명명 규칙 일관성 부족
- 응답 표준 부재
- 보안/설정/운영 방식이 코드 전반에 흩어짐
- 일부 하드코딩 데이터 존재
- 코드 인코딩 깨짐 흔적이 많아 가독성과 온보딩성이 떨어짐

## 테스트 가능성 분석

확인 결과:

- `src/test` 하위 테스트 코드 없음
- 테스트 리포트 산출물 없음
- 즉, 자동화 테스트 체계는 사실상 미구축 상태

의미:

- 리팩터링 안전장치 부족
- 현장 연계 기능 수정 시 회귀 검증 비용 증가
- 협업 시 “감으로 배포”되는 위험이 큼

## CI/CD 및 자동배포 관점 분석

### 현재 상태

- Git 저장소는 존재
- CI/CD 설정 파일은 확인되지 않음
- 컨테이너화 정의 없음
- 배포 스크립트/릴리스 파이프라인 정의 없음
- 운영/개발 환경 promotion 흐름 없음

### 의미

현재는 다음이 암묵지에 의존할 가능성이 높다.

- 누가 빌드하는가
- 어떤 환경파일로 배포하는가
- 배포 순서가 무엇인가
- 장애 시 롤백은 어떻게 하는가
- 현장 MCU/웹앱 버전 호환은 어떻게 맞추는가

### 자동배포 관점에서 특히 위험한 점

- 운영 비밀정보가 코드에 포함
- 외부 장비/외부 API 호출이 코드 실행만으로 발생
- 현장 디바이스와 메시지 계약 버전 관리 부재
- 데이터베이스 마이그레이션 체계 부재

## 협업 관점 분석

### 현재 협업을 어렵게 만드는 요소

- 기능별 문서 부재
- API 문서 부재
- 메시지 스키마 문서 부재
- 환경셋업 표준 부재
- 테스트 부재
- CI 부재
- 배포 파이프라인 부재
- 운영 규칙과 개발 규칙 혼재

### 팀 확장 시 예상되는 문제

- 백엔드/프런트/임베디드 팀 간 계약 충돌
- “이 필드가 꼭 필요한가”를 코드 grep으로만 확인해야 함
- 실시간 기능 수정 시 영향 범위가 넓음
- 현장 장애 원인 추적이 사람 의존적일 가능성 높음

## 관찰된 구체적 리스크

### 1. 비밀정보 하드코딩

- DB 계정/비밀번호
- JWT secret
- 외부 API key
- 내부 Nexus 자격증명

### 2. 보안 경계 약함

- `/api/**` 광범위 permitAll
- WebSocket 사실상 개방형
- 인증 주입이 `guest`

### 3. API/메시지 계약 문서 부재

- Swagger 사실상 미활용
- WebSocket payload 스키마 미정의
- UDP 프로토콜 코드 의존

### 4. 프런트 하드코딩

- 정류장 정보 중복/하드코딩
- 화면 JS가 운영 규칙을 직접 품음

### 5. 테스트/배포 자동화 부재

- 코드 변경의 안전성 낮음
- 협업 생산성 저하

### 6. 인프라와 도메인 결합

- 라우터 로그인 기능이 애플리케이션 내부에 직접 존재
- 파일 업로드 경로/환경설정이 강결합

### 7. 데이터 수명주기 설계 부족

- 일부 데이터는 3일 단위 truncate
- 어떤 이력이 얼마나 필요한지 정책화가 코드에서 잘 드러나지 않음

## REST API + Swagger 분리 고도화 판단을 위한 관찰 포인트

이번 단계에서는 방안을 제시하지 않고, 판단 재료만 정리한다.

### REST API/Swagger 중심 분리에 유리한 신호

- 이미 `/api/**` 하위에 기능군이 상당수 존재
- 프런트와 백엔드의 관심사를 분리할 여지가 있음
- 운영 화면을 별도 프런트 앱으로 전환할 기반이 일부 존재
- 외부 연계/관리자 기능 문서화 필요성이 큼

### 단순 API 분리만으로는 부족한 신호

- 핵심 가치는 실시간 제어와 현장 메시징
- WebSocket/UDP/디바이스 제어 계약이 더 중요함
- 운영 화면보다 디바이스 통신 계층 정리가 먼저일 수 있음
- 현행 구조는 “API 서버”보다 “운영 허브” 성격이 강함

즉, 다음 페이즈에서는 “Swagger 붙인 REST 분리”만으로 충분한지, 아니면 **실시간 제어 중심의 차세대 구조 재설계**가 필요한지를 함께 판단해야 한다.

## 차세대 형식 고도화 판단을 위한 핵심 질문

다음 페이즈에서 반드시 답해야 할 질문들이다.

1. 이 시스템의 중심은 관리자 웹인가, 실시간 장비 운영 허브인가
2. 디바이스 메시지 계약을 제품 수준으로 관리해야 하는가
3. 현장 MCU 펌웨어와 서버 버전 호환 전략이 필요한가
4. 운영 화면과 디바이스 메시지 중계 책임을 분리할 것인가
5. 기상/대기질은 부가 기능인가, 운영 정책 입력인가
6. 정류장/장비/상태/이력/명령을 별도 도메인으로 분리할 것인가
7. 내부 관리용 API와 외부/현장 연계용 API를 구분할 것인가
