# 네트워크 복원력 기능 세부 수행계획

## 1. 목적

원격지 단말의 네트워크 장애를 감지하고, 운영 화면에서 장애 이력과 장애 로그를 빠르게 확인할 수 있도록 기능을 단계적으로 완성한다.

이번 계획은 현재 저장소에 반영된 다음 변경을 기준선으로 삼는다.

- `tb_monitoring`, `tb_terminal_network_status`에 네트워크 장애 로그 raw 필드 추가
- `tb_terminal_network_outage_log` 신규 테이블 추가
- 모니터링 수신 시 `network_outage_logs` 저장 로직 추가
- 장애 로그 조회용 `/api/iot/network-outage-logs` API 추가
- 모니터링 팝업에 최근 네트워크 장애 로그 영역 추가
- `MonitoringServiceTest`에 장애 로그 파싱/저장 테스트 추가

## 2. 전체 추진 원칙

- 기존 모니터링 흐름을 깨지 않는 최소 변경으로 진행한다.
- DB 스키마, 수집 로직, 조회 API, 운영 UI를 같은 페이즈 안에서 닫는다.
- 각 페이즈 종료 시점마다 테스트 또는 실행 검증이 가능한 상태를 만든다.
- 사용자 변경과 무관한 리팩터링은 뒤로 미룬다.

## 3. 페이즈별 계획

### Phase 1. 수집 안정화

목표:
라즈베리파이/단말에서 올라오는 네트워크 장애 payload를 누락 없이 저장하고, 비정상 payload에도 서비스가 흔들리지 않도록 한다.

작업:
- `network_outage_logs`가 배열/문자열 두 형식 모두 들어올 때 저장되도록 유지
- 잘못된 JSON 입력 시 raw 값은 보존하고 장애 로그 적재는 건너뛰도록 유지
- 중복 로그 방지를 위한 hash 정책 검증
- 단말별 최근 로그 보관 개수 정책 확인

산출물:
- 서비스 로직 반영
- Mapper SQL 반영
- 단위 테스트 보강

완료 기준:
- `MonitoringServiceTest` 관련 케이스 통과
- 동일 로그 재수신 시 중복 insert가 발생하지 않음

상태:
진행 중. 현재 코드 기준으로 핵심 저장 경로와 테스트가 1차 반영되어 있다.

### Phase 2. 운영 조회 완성

목표:
운영자가 모니터링 화면에서 장애 상태와 장애 로그를 바로 해석할 수 있게 한다.

작업:
- 팝업의 장애 이력과 장애 로그를 분리해 표시
- 시간, 등급, 로거, 메시지 컬럼 표시 기준 정리
- 빈 데이터, 지연 응답, 조회 실패 시 UI 문구 통일
- 필요 시 최근 로그 개수와 정렬 기준 조정

산출물:
- `monitoring.html` UI 반영
- `monitoring.js` 조회/렌더링 로직 반영
- 운영 확인 체크리스트

완료 기준:
- 단말 클릭 시 장애 이력과 장애 로그가 모두 노출됨
- 조회 실패 시 화면이 깨지지 않고 기본 문구가 유지됨

상태:
진행 중. 최근 네트워크 장애 로그 테이블과 AJAX 조회는 반영되어 있다.

### Phase 3. API 및 계약 정리

목표:
장애 로그 조회 인터페이스를 운영 기능 관점에서 안정적으로 재사용할 수 있게 정리한다.

작업:
- `/api/iot/network-outage-logs` 요청/응답 계약 문서화
- `terminal_id` 필수값 검증과 예외 응답 방식 정리
- 향후 검색 조건 확장 가능 여부 검토
- 모니터링 API와 IoT API의 책임 경계 재점검

산출물:
- API 명세 초안
- 입력값 검증 정책
- 후속 리팩터링 후보 목록

완료 기준:
- 운영팀/개발팀이 같은 요청 규격으로 조회 가능
- 잘못된 파라미터에 대한 동작이 명확함

상태:
착수 전.

### Phase 4. 운영 대응력 강화

목표:
장애 감지 이후 원인 추적과 후속 대응까지 이어질 수 있도록 관측성과 운영 절차를 보강한다.

작업:
- 장애 로그 저장 실패, 조회 실패에 대한 서버 로그 기준 정리
- 장애 발생 시점과 복구 시점 연결 규칙 검토
- 필요 시 재부팅 요청 이력과 장애 로그 연계
- 운영 문서에 확인 순서와 장애 판별 기준 정리

산출물:
- 운영 점검 절차
- 추가 로그/알림 개선안
- 후속 개발 백로그

완료 기준:
- 장애 발생 시 운영자가 확인해야 할 화면과 데이터가 정리됨
- 로그만 보고도 기본 원인 구분이 가능함

상태:
착수 전.

## 4. 즉시 실행 순서

1. Phase 1 검증
   `MonitoringServiceTest`를 실행해 현재 저장 경로를 확인한다.
2. Phase 2 화면 점검
   운영 팝업에서 장애 로그 렌더링과 빈 상태 메시지를 확인한다.
3. Phase 3 계약 정리
   API 파라미터와 응답 형식을 문서 또는 주석으로 고정한다.

## 5. 이번 체크포인트 의미

이번 커밋은 네트워크 장애 복원력 작업의 1차 구현 완료 지점이다.
즉, "장애 로그를 받는다 -> 저장한다 -> 조회한다 -> 운영 화면에서 본다"까지의 기본 흐름을 연결한 상태이며,
다음 작업은 이 흐름의 안정화와 계약 정리에 집중한다.
