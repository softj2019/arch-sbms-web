# SBMS 고도화 방안 제안서 (2차)

## 문서 목적

이 문서는 [`analysis-phase1-current-state.md`](/D:/home/sbms/docs/analysis-phase1-current-state.md)에서 정리한 현행 분석 결과를 바탕으로,
SBMS를 **유지보수, 협업, CI/CD, 자동배포, 운영 안정성에 유리한 환경**으로 리마스터링하기 위한 고도화 방안을 제시한다.

이번 문서의 목표는 다음과 같다.

- 현행 구조를 어떤 방향으로 고도화할지 결정 기준 제시
- “REST API + Swagger 분리 고도화”와 “차세대 구조 전환”을 비교
- 현장 MCU/라즈베리파이 기반 운영 특성을 유지하면서도 구조를 개선하는 방법 제안
- 빅뱅 재개발이 아닌 단계적 전환 로드맵 제시

## 결론 요약

SBMS는 단순한 관리자 웹사이트가 아니라 **현장 단말 운영 허브**다.
따라서 단순히 REST API를 정리하고 Swagger를 붙이는 수준만으로는 장기 유지보수 문제를 해결하기 어렵다.

권장 방향은 다음과 같다.

### 권장 전략

**단계적 차세대화**

1. 단기:
   현행 Spring Boot 모놀리스를 안정화한다.
   설정 분리, 비밀정보 제거, 테스트 기반 마련, CI 구축, API 문서화, 메시지 계약 문서화부터 시작한다.

2. 중기:
   운영 화면, 관리자 API, 실시간 메시지 허브, 외부 연계, 배치/수집 로직을 논리적으로 분리한다.
   이 단계에서 Swagger 기반 REST 정비를 함께 진행한다.

3. 장기:
   실시간 제어/수집 중심의 차세대 구조로 전환한다.
   핵심은 “웹 MVC”가 아니라 “디바이스 운영 플랫폼” 구조로 바꾸는 것이다.

즉, **1단계는 현행 시스템 리마스터링**, **2단계는 API 제품화**, **3단계는 실시간 운영 플랫폼화**가 적절하다.

## 왜 단순 Swagger 정리만으로는 부족한가

현행 시스템의 핵심 가치는 아래에 있다.

- 디바이스 상태 실시간 수집
- 디바이스 제어 명령 송수신
- WebSocket/STOMP 토픽 기반 운영
- UDP 패킷 파싱과 브로드캐스트
- HID/재실 감지 로그
- 기상/대기질 기반 운영 연계

즉, REST API는 시스템의 한 부분일 뿐이고, 실제 복잡도는 **메시지 계약과 운영 흐름**에 있다.

그래서 Swagger만 정리하면 해결되는 영역:

- 관리자 CRUD API 문서화
- 프런트-백엔드 HTTP 인터페이스 정리
- 협업 시 API 가시성 개선

Swagger만으로 해결되지 않는 영역:

- 현장 MCU와 서버 간 메시지 계약
- 실시간 제어 ack/retry/timeout
- 상태 스트림 모델링
- UDP 프로토콜 안정성
- 운영/관제/알람 체계
- 펌웨어/서버 버전 호환성

따라서 **Swagger는 필요하지만, 중심 해법은 아니다**.

## 아키텍처 방향 제안

## 제안 1. 단기 리마스터링 목표 구조

단기에는 현행 모놀리스를 유지하되, 내부 구조를 다음 5개 축으로 분리한다.

1. 관리자 웹 계층
2. 내부 API 계층
3. 실시간 메시징 계층
4. 외부 연계/수집 계층
5. 공통 인프라 계층

### 권장 패키지 분리 예시

```text
com.archivsoft.sbms
  admin        # Thymeleaf 화면, 관리자 UI 전용
  api          # REST API
  realtime     # WebSocket/STOMP, command, event, session
  device       # MCU/단말/라우터/Wi-Fi/HID/CV 도메인
  weather      # 기상/대기질 연계
  facility     # 정류장/설비/장비 메타데이터
  auth         # 인증/권한/JWT
  shared       # 공통 응답, 예외, 유틸, 설정
  infra        # DB, 캐시, 파일, 외부 클라이언트, 스케줄러
```

이 단계는 “기능 재개발”보다 “책임 분리와 경계 정리”가 우선이다.

## 제안 2. 중기 목표 구조

중기에는 논리 분리를 넘어 배포 단위를 나누는 방향이 적합하다.

### 권장 서비스 경계

1. `sbms-admin`
   관리자 웹 및 관리자 API

2. `sbms-realtime-hub`
   WebSocket/STOMP, 명령 송수신, 실시간 상태 브로드캐스트

3. `sbms-device-ingest`
   MCU/단말 payload, UDP 수신, HID/CV/Wi-Fi 입력 수집

4. `sbms-environment`
   기상/대기질 수집과 표시 정책

5. `sbms-auth`
   인증/권한/토큰/세션

이때도 반드시 물리적 마이크로서비스까지 바로 가야 하는 것은 아니다.
먼저 **모듈형 모놀리스**로 시작하고, 경계가 안정되면 분리하는 방식이 현실적이다.

## 제안 3. 장기 목표 구조

장기적으로는 다음 구조가 가장 적합하다.

- 관리자 포털: 별도 웹앱
- API 게이트웨이: 인증/권한/라우팅
- 디바이스 게이트웨이: WebSocket/MQTT/STOMP/UDP 수용
- 이벤트 버스: 상태/명령/알림 전달
- 운영 데이터 저장소: 최신 상태 + 이력 저장 분리
- 배치/수집 서비스: 기상/대기질/외부 API

즉, “웹앱” 중심이 아니라 **실시간 이벤트 기반 운영 플랫폼**으로 보는 관점이 맞다.

## REST API + Swagger 고도화 방안

## 목표

관리자 기능과 프런트 협업 효율을 위해 REST API를 제품 수준으로 정리한다.

## 반드시 해야 할 작업

### 1. API 네이밍 정규화

현재:

- `shallList`
- `addShall`
- `msgList`
- `getLogList`
- `listSimple`

개선 예:

- `GET /api/v1/commands`
- `POST /api/v1/commands`
- `GET /api/v1/control-logs`
- `GET /api/v1/facilities`
- `GET /api/v1/facilities/simple`

### 2. 버전 도입

권장:

- `/api/v1/**`

이유:

- 차세대 프런트와 현행 UI를 병행할 수 있음
- 현장 장비와 관리자 화면의 변경 속도를 분리 가능

### 3. 응답 형식 표준화

권장 표준 예:

```json
{
  "success": true,
  "code": "OK",
  "message": "요청이 성공했습니다.",
  "data": {},
  "meta": {}
}
```

에러 표준 예:

```json
{
  "success": false,
  "code": "AUTH-401",
  "message": "인증이 필요합니다.",
  "errors": []
}
```

### 4. Swagger/OpenAPI 실제 도입

필수 작업:

- `@Tag`, `@Operation`, `@Schema` 적용
- 요청/응답 DTO 정리
- 인증이 필요한 API와 아닌 API 구분
- WebSocket/UDP는 OpenAPI 외 별도 문서 체계로 분리

### 5. 관리자용 API와 디바이스용 API 분리

관리자 API:

- 사용자
- 권한
- 시설
- 설정
- 로그
- 조회/통계

디바이스/실시간 API:

- 명령
- 상태
- 현장 설정
- 실시간 이벤트

같은 `/api` 아래 두더라도 문서/권한/버전은 분리해야 한다.

## 실시간 메시지 고도화 방안

이 시스템에서 가장 중요한 고도화 대상이다.

## 권장 핵심 원칙

### 1. 메시지 계약을 명세화

현재는 JSON key와 STOMP topic이 사실상 계약이다.
이를 다음처럼 문서화해야 한다.

- 토픽명
- 송신 주체
- 수신 주체
- payload schema
- 필수 필드
- 선택 필드
- 예시 메시지
- 버전
- 오류 처리 규칙

### 2. 메시지 타입 분리

권장 유형:

- 상태 이벤트
- 명령 요청
- 명령 응답
- 설정 동기화
- 알림 이벤트
- 장애 이벤트

### 3. 공통 Envelope 도입

권장 예:

```json
{
  "eventType": "DEVICE_STATUS_UPDATED",
  "version": "1.0",
  "timestamp": "2026-03-11T14:30:00+09:00",
  "terminalId": "26019",
  "source": "raspberrypi",
  "payload": {}
}
```

장점:

- 프런트와 백엔드, 디바이스 간 계약이 안정화
- 버전 호환 관리 가능
- 이벤트 감사 및 재처리 용이

### 4. 명령 처리 상태 모델 도입

현재는 명령을 브로드캐스트하고 끝나는 허브형 구조에 가깝다.
차세대에는 최소한 다음 상태가 필요하다.

- requested
- delivered
- accepted
- executed
- failed
- timeout

### 5. 장비별 capability 모델 도입

정류장마다 장비 구성이 다르므로, 명령 가능 여부를 정적 하드코딩이 아니라 capability로 다뤄야 한다.

예:

- screen.control
- led.message
- wifi.monitoring
- cv.stream
- air.display

## MCU/라즈베리파이 연계 고도화 방안

## 현재 구조의 장점

- 단말에서 직접 상태 송신
- 서버가 빠르게 브로드캐스트
- 운영 UI가 즉시 반응

## 개선 방향

### 1. 디바이스 프로토콜 문서화

다음 항목 문서화 필요:

- 연결 방식
- 인증 방식
- heartbeat 주기
- 상태 payload schema
- 명령 수신 schema
- 에러 응답 schema
- 펌웨어 버전 관리 규칙

### 2. 펌웨어/서버 호환 버전 체계

필수:

- `protocolVersion`
- `firmwareVersion`
- `serverCompatibleRange`

### 3. 단말 등록/인증 체계

현재는 terminal_id 중심 추정 구조다.
향후에는 다음이 필요하다.

- 디바이스 등록
- 단말 키/토큰
- terminal_id와 물리 디바이스 식별자 매핑
- 비인가 단말 차단

### 4. 메시지 재전송/헬스체크

현장 환경 특성상 반드시 고려해야 한다.

- 마지막 heartbeat 시간
- offline 판단 기준
- 명령 timeout
- 재전송 횟수
- ack 누락 알람

### 5. MQTT 검토

다음 페이즈에서 검토할 가치가 높다.

이유:

- 디바이스 친화적
- QoS 선택 가능
- 상태/명령 토픽 관리 용이
- 현장 네트워크 불안정 시 복원력 향상 가능

단, 지금 당장 전환보다는 **STOMP 계약 안정화 후 비교 검토**가 현실적이다.

## 기상/대기질 연계 고도화 방안

## 방향

기상/대기질을 “정보 조회 기능”이 아니라 **운영 도메인 서비스**로 재정의해야 한다.

### 권장 분리

1. 수집
   외부 API 호출과 저장

2. 해석
   현재 표시용 지표와 상태 판단

3. 정책
   어떤 값을 현장 설정/표시와 연계할지 결정

4. 제공
   관리자용 API, 디바이스용 설정, 화면용 조회

### 이유

현재는 한 서비스가 모두 수행한다.
이 구조는 변경 시 영향 범위가 넓다.

## 유지보수 관점 리마스터링 우선순위

### 최우선

1. 설정/비밀정보 분리
2. API/메시지 계약 문서화
3. 테스트 기반 도입
4. CI 구축
5. 보안 경계 재정비

### 그 다음

6. 패키지/도메인 구조 재정리
7. 프런트 하드코딩 제거
8. 실시간 명령 상태 모델 도입
9. 운영 로그/관측성 강화

### 중장기

10. 관리자 UI 분리
11. 실시간 허브 분리
12. 디바이스 게이트웨이 표준화

## 보안 고도화 방안

## 반드시 해야 할 것

### 1. 비밀정보 코드 제거

- DB 계정
- JWT secret
- 외부 API key
- Nexus credentials

대체:

- 환경변수
- Secret Manager
- 배포 파이프라인 주입

### 2. 인증/인가 재정비

- `/api/**` 무조건 `permitAll()` 제거
- 관리자 API에 역할 기반 인가 적용
- WebSocket 연결/구독/발행 권한 분리

### 3. WebSocket 인증 표준화

현재 `guest` 고정 주입 방식은 제거해야 한다.
대안:

- JWT 기반 handshake 인증
- user destination 분리
- command topic 권한 체크

### 4. CORS 정상화

- 허용 origin 명시
- `*`와 credential 동시 사용 금지

### 5. 감사 로그 체계

- 누가 어떤 정류장에 어떤 명령을 보냈는지
- 성공/실패/timeout
- 변경 전후 상태

이 데이터는 운영 감사와 장애 추적에 필수다.

## 현실적 단계

### 1단계

- jQuery 유지

### 2단계

### 3단계

즉, 프런트는 “지금 당장 전면 재작성”보다 **구조 정리 후 단계적 전환**이 합리적이다.

## REST 분리안 vs 차세대 구조안 비교

## 안 A. 현행 모놀리스 유지 + REST/Swagger 정비

### 장점

- 빠르게 시작 가능
- 현장 영향 적음
- 관리자 기능 협업 생산성 개선
- 문서화/테스트/CI 도입이 수월

### 한계

- 실시간 허브 구조의 근본 문제는 남음
- 디바이스 계약 관리가 부족
- 장기 확장성 제한

### 적합성

- 단기에는 필수
- 장기 단독 해법으로는 부족

## 안 B. 모듈형 모놀리스로 리마스터링

### 장점

- 코드 복잡도를 가장 현실적으로 낮출 수 있음
- 배포 부담을 급격히 늘리지 않음
- 서비스 분리 준비가 가능

### 한계

- 조직 차원에서 경계 discipline이 필요

### 적합성

- 가장 추천하는 중간 단계

## 안 C. 차세대 이벤트 기반 운영 플랫폼 전환

### 장점

- 현장 운영형 시스템에 가장 잘 맞음
- 디바이스/실시간/운영 UI를 분리 가능
- 장기적으로 협업성과 확장성이 높음

### 한계

- 설계와 전환 비용 큼
- 운영 중 전환 전략이 필수

### 적합성

- 장기 목표로 적합
- 즉시 빅뱅 전환은 비권장

## 최종 권고안

### 최종 권장 시나리오

**안 B를 즉시 시작하고, 안 C를 목표 아키텍처로 둔다.**

즉:

- 지금 바로 할 일:
  모듈형 모놀리스 리마스터링 + API/Swagger 정비 + 보안/설정/테스트/CI/CD 구축

- 이후 목표:
  실시간 허브와 디바이스 수집 계층을 분리하는 차세대 운영 플랫폼화

이 전략이 가장 현실적이고, 현장 운영 리스크도 낮다.

## 단계별 실행 로드맵

## Phase 0. 안정화 준비

기간 권장: 1~2주

- 프로파일 정리
- 개발/운영 환경 분리
- 기본 README/운영 문서 작성
- 브랜치 전략 및 PR 규칙 수립

## Phase 1. 품질 기반 구축

- 테스트 프레임 구축

- CI 파이프라인 구축

## Phase 2. API/계약 정비

기간 권장: 3~5주

- REST API 버전 도입

- WebSocket topic/payload 명세서 작성
- UDP 프로토콜 문서화
- 관리자 API와 디바이스 API 논리 분리

## Phase 3. 도메인 리팩터링

기간 권장: 4~8주

- facility/device/realtime/weather/auth 모듈 분리
- 서비스 책임 재배치
- 프런트 하드코딩 제거
- 메시지 envelope 도입

## Phase 4. 운영 플랫폼화 준비

기간 권장: 4~8주

## Phase 5. 차세대 분리 전환

- 실시간 허브 분리
- 관리자 포털 분리
- 디바이스 게이트웨이 분리
- 이벤트 기반 구조 도입

## 성공 기준

고도화가 성공했는지 판단하는 기준은 아래와 같다.

### 기술 지표

- 테스트 자동화 존재
- CI 자동 실행
- 환경별 자동배포 가능
- API/메시지 문서 존재
- 비밀정보 저장소 제거
- 장애 추적 가능

### 운영 지표

- 현장 장비 상태 추적 가능
- 명령 성공/실패 추적 가능
- 문제 발생 시 원인 구간 식별 가능
- 운영자 화면 변경이 디바이스 계약을 쉽게 깨지 않음

### 협업 지표

- 신규 개발자가 문서만으로 진입 가능
- 프런트/백엔드/임베디드 간 계약 충돌 감소
- 배포 절차가 사람 의존에서 시스템 의존으로 전환

## 제안 마무리

SBMS는 고도화 가치가 높은 프로젝트다.
이유는 단순 CRUD 시스템이 아니라, **현장 디바이스 운영, 실시간 메시지, 환경 데이터, 관리자 기능**이 함께 있는 플랫폼형 시스템이기 때문이다.

따라서 다음 원칙이 중요하다.

- 웹앱처럼 고치지 말고 운영 플랫폼처럼 다룰 것
- Swagger는 필요하지만 시작점일 뿐이라는 점을 분명히 할 것
- MCU/라즈베리파이/현장 제어 흐름을 중심축으로 설계할 것
- 빅뱅 재개발 대신 단계적 리마스터링으로 갈 것

최종적으로 권장하는 방향은 다음 한 줄로 요약된다.

**현행 모놀리스를 품질 기반으로 리마스터링한 뒤, 실시간 운영 허브 중심의 차세대 구조로 단계적으로 전환한다.**
